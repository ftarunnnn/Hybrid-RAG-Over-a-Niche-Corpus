HTTP/1.1, HTTP/2, HTTP/3 and TLS 1.3 Technical Reference

Standardization: RFC 7540, RFC 8446, RFC 9114

Protocol Evolution from HTTP/1.1 to HTTP/3

HTTP/1.1 Limitations

HTTP/1.1 (RFC 2616) introduced persistent connections via the Keep-Alive header, reducing the need to initiate a new TCP handshake for every asset. However, HTTP/1.1 suffered from severe Head-of-Line (HoL) Blocking at Layer 7: requests on a single connection had to be processed strictly sequentially. Modern browsers worked around this by opening up to 6 parallel TCP connections per domain, causing TCP congestion and slow start overhead.

HTTP/2 Binary Framing and Multiplexing

HTTP/2 (RFC 7540) solved Application-Layer HoL blocking by replacing plain-text formatting with a binary framing layer. Multiple independent streams are interleaved concurrently across a single underlying TCP connection. Features include HPACK header compression, stream prioritization, and Server Push. However, because HTTP/2 relies on TCP, any single lost IP packet stalls all multiplexed streams in the TCP buffer—a phenomenon known as Transport-Layer TCP HoL Blocking.

HTTP/3 and QUIC Protocol

HTTP/3 (RFC 9114) eliminates Transport-Layer HoL blocking by replacing TCP with QUIC (RFC 9000), which runs on top of UDP port 443. In QUIC, packet loss on one stream affects only that specific stream, allowing other streams to continue uninterrupted. QUIC natively integrates TLS 1.3 encryption directly into the transport handshake, achieving 0-RTT connection re-establishment and seamless Connection ID migration across network switches (e.g., transitioning from Wi-Fi to cellular data).

TLS 1.3 Cryptographic Handshake Architecture

Transport Layer Security (TLS) version 1.3 (RFC 8446) overhauled the security and latency of encrypted communications compared to TLS 1.2.

Key Improvements over TLS 1.2

  • 1-RTT Full Handshake: Reduced standard connection establishment latency from 2 Round Trips in TLS 1.2 to exactly 1 Round Trip in TLS 1.3.
  • Deprecation of Insecure Algorithms: Completely removed RSA key exchange, CBC-mode ciphers, RC4, MD5, SHA-1, and static Diffie-Hellman. Only Authenticated Encryption with Associated Data (AEAD) ciphers are permitted (AES-GCM, ChaCha20-Poly1305, AES-CCM).
  • Mandatory Perfect Forward Secrecy (PFS): Requires Ephemeral Diffie-Hellman (ECDHE or DHE) key exchange so past recorded traffic cannot be decrypted even if the server private key is compromised in the future.

TLS 1.3 1-RTT Handshake Sequence

  1. ClientHello: Client transmits supported cipher suites, supported elliptic curves (e.g., x25519), and precomputes its ephemeral key share (KeyShare extension) inside the initial message.
  2. ServerHello: Server selects the cipher suite, chooses a matching elliptic curve, and returns its own ephemeral KeyShare along with its encrypted Certificate and CertificateVerify payload.
  3. Key Derivation: Both client and server immediately derive the symmetric session keys (HKDF - HMAC-based Key Derivation Function). Application data encryption begins immediately with 1-RTT latency.
